# Controls, navigation, and overlays: requirement comparison

Audit date: 2026-09-09. Mash source baseline: `d2e022716087235782e4799d0bbeb8f2042fe9f8`; supplied reference checkout: `48336016a3074fbb8af619014b18565ef747f512`. This is a source comparison, with previous interaction results identified separately. The initial inventory was read-only; subsequent focused source-browser checks are recorded below. Complete visual equivalence is **not established**.

The existing [capability checklist](../reference/components.json) was read first. Its `examples` arrays are historical, not the effective registry. Its feature headings also omit substantial story-only requirements: split buttons, deep context submenus, selection overflow/pinning, variable-height command rows, and several disclosure arrangements.

## Current checkpoint

The requirement tables below now describe the final effective source registry, while keeping stable reference-document/story line evidence. Source coverage, focused interaction tests and integrated production visual acceptance are distinct. The integrated sweep is still in progress; no count establishes visual parity.

The evaluated direct registry contains **85 component tags and 390 example entries**. These are authored registry entries before child aliases/fallback schema examples. The component-by-component appendix below gives exact names/counts for this audit's scope. Shared examples appearing on two component pages count as two registry entries, not two independent implementations.

This pass added supported form/selection/input/navigation/menu/modal compositions through `selection.ts`, `control-states.ts`, `workflows.ts`, `menu-extensions.ts`, `navigation-overlays.ts` and `final-control-examples.ts`. Existing useful variants remain; the same-named inert `Form` was replaced. The final module contributes nine arrangements, including form layout/span/size controls, OTP resend/custom sizes, combobox rich grid/collapsed chips, custom accordion disclosure, connected toggles and no-title/update alerts.

True capability gaps still include command virtualization, command custom query/ranking integration, general caret-aware editable masking/numeric formatting, complete replacement of the fixed combobox edit trigger, explicit multi-select tree semantics, toggle treatment policy and the differing rating decrement interaction. Chip overflow/pinning/selection limits, grouped OTP, connected geometry, form layouts and no-title alert examples are now implemented and must not be listed as missing capabilities.

Remaining example-only and acceptance gaps are stated in the individual rows. Notable remaining examples include tree loading/search/icons, textarea-specific growth/editing, custom input context/masking treatments, material/contrast matrices, menu corner/collision variants and some specialized settings/sheet/list shapes. The radio size specimen now uses inherited semantic type and indicator tokens on each group; it no longer implies an unsupported radio `size` API. A visual comparison of those scoped sizes remains open.

## How to read the evidence

- `D(topic):line` means `website/component/topic.md` in the supplied reference checkout. `S(topic):line` means `crates/story/src/stories/topic_story.rs` there. Topic filenames use underscores in stories. The checkout revision above makes those line references stable. Reference prose is white-labelled here.
- `E` means the requirement is visibly represented in effective example source; it is not a fresh interaction or visual acceptance claim. `P` means only part of the requirement is demonstrated. `G` means a missing example. `C` identifies a source-level capability or contract gap. `V` identifies a specifically previously passed interaction, with test evidence below.
- Import instructions, duplicate API listings, platform setup boilerplate, migration notes, and general best-practice prose are not separate examples. The tables cover their observable behavior where applicable. Native application title bars/window controls are identified as a platform adaptation, not silently counted as web-component parity.
- A working example on a different component page is named explicitly as cross-coverage. It does not make the target component's page complete.

The effective registry was evaluated from the actual TypeScript modules, not inferred from declarations. Resolution is `controlExamples[tag] ?? componentExamples[tag]` in [examples.ts](../../apps/catalog/src/examples.ts). `components.ts` applies navigation/refinement/display/feedback/layout and specialized modules, then appends the scoped control/workflow modules. `controls.ts` owns its matching tags and merges the applicable pattern/selection/state/menu/final-control modules. Thus a refinement for a tag owned by `controls.ts` would not replace the effective control catalogue. Child pages fall back to a selected parent example through `compositionsByTag`; they do not automatically receive every parent variant.
